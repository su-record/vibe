# 독립 편집 검증

이 절차는 기자, 칼럼니스트, 편집 책임자나 외부 기관에 제출할 한국어 원고에 적용한다.
일상적인 메일, 메모와 초안에는 자동으로 적용하지 않는다.

## 원칙

- 작성자와 심사자는 서로 다른 에이전트여야 한다. 작성자가 심사자 역할을 흉내 내며 자체 판정하지 않는다.
- 심사자에게 작성 과정, 작성자의 자기평가와 의도한 정답을 주지 않는다.
- 심사자는 원고를 대신 써 주지 않는다. 정확한 반려 지점, 독자에게 미치는 영향과 수정 조건만 반환한다.
- 문체 취향과 결함을 구분한다. 위치와 영향을 특정할 수 없는 취향 차이는 반려 사유가 아니다.
- 형식에 맞는 모든 반려 항목은 수정하거나 사람에게 넘긴다. 작성 에이전트가 임의로 무효화하거나
  일부만 골라 반영할 수 없다.

## 심사자

두 심사자는 vibe 패키지의 `reviewers/ko/` 에 프롬프트로 들어 있고, 같은 내용이 클라이언트 에이전트로도
설치된다 (Claude Code 는 `agents/ko-copy-editor.md`·`agents/ko-chief-editor.md`, Codex 는 플러그인 트리의
`agents/*.toml`).

| 단계 | 심사자 | 역할 |
|---|---|---|
| 1차 | `ko-copy-editor` | 교열 심사자: 문장·규범·표기 결함 판정 |
| 2차 | `ko-chief-editor` | 편집장 심사자: 게재·제출 가능 여부 판정 |

## 하네스가 심사한다

vibe 안에서는 심사를 모델이 돌리지 않는다. 원고에 `review` 검사를 묶은 시나리오를 두고 `vibe check` 로
하네스가 두 심사자를 차례로 띄운다.

```yaml
- id: column-review
  then: the column passes the copy editor and the chief editor
  check: { type: review, path: out/column.md, contract: out/contract.md, evidence: out/evidence.md }
```

- `path` 는 심사할 원고 전문, `contract` 는 편집 계약, `evidence` 는 근거 장부다. 둘은 생략할 수 있지만
  제출용 원고에는 둘 다 파일로 둔다. `lang` 을 적지 않으면 원고의 문자로 판별한다.
- 하네스는 `reviewers/ko/copy-editor.md` 를 먼저, 통과하면 `reviewers/ko/chief-editor.md` 를 띄운다.
  응답 전체가 정확히 `PASS` 한 줄일 때만 그 단계가 통과다. `REJECT` 목록과 형식이 다른 응답은 모두
  실패이고, 응답은 evidence 의 `tail` 에 남는다.
- 같은 실패가 두 번 이어지면 하네스가 STUCK 으로 멈추고 인박스에 묻는다. 작성자는 `REJECT` 항목을
  최소 범위로 고친 뒤 `vibe check` 를 다시 돌린다. 근거와 충돌하거나 취향만을 강요하는 항목이라
  수정할 수 없으면 버리지 말고 충돌 내용과 함께 `vibe ask` 로 넘긴다.

## 심사자 입력 묶음

하네스는 각 심사자에게 다음만 전달한다. 작성 과정과 작성자의 자기평가는 넣지 않는다.

1. 편집 계약: 매체, 꼭지, 독자, 목적, 분량, 어조, 표기 원칙과 마감 상태.
2. 근거 장부: 사실·수치·인용과 출처, 필자의 경험·해석, 확인하지 못한 사항.
3. 심사할 원고 전문: 제목, 본문, 표, 주석과 출처를 생략하지 않는다.

입력 묶음에 실제 제출 규격이나 핵심 근거가 없으면 심사자는 심사를 진행한 척하지 말고 `NEEDS-HUMAN` 으로
돌려보낸다. 하네스는 그것도 실패로 기록한다.

## vibe 밖에서

하네스 없이 이 스킬만 있는 환경에서는 같은 두 심사자를 별도 에이전트로 직접 띄운다 (Claude Code 는
Agent 도구, Codex 는 서브에이전트 스폰). 1차가 `PASS` 한 뒤에만 2차를 부르고, 완료된 호출 결과만
판정에 쓴다. 에이전트를 띄울 수 없으면 독립 검증을 거쳤다고 말하지 말고 사람의 편집 검토가 필요하다고
밝힌다.

## 위임 실패 처리

- 완료된 에이전트 호출 결과만 판정에 사용한다. 백그라운드 작업의 시작 응답, 진행 로그와
  에이전트의 자기보고는 `PASS`가 아니다.
- `PASS`는 앞뒤 공백을 제거한 전체 응답이 정확히 `PASS` 한 줄일 때만 인정한다. `PASS` 뒤에
  설명·경고·조건이 붙으면 통과가 아니다. 그 밖의 응답은 완전한 `REJECT` 형식을 갖춰야 하며,
  도구 오류, 시간 초과, 빈 응답, 잘린 응답과 형식이 다른 응답은 모두 심사 실패다.
- 심사 실패 때 같은 입력으로 같은 종류의 심사를 한 번만 다시 돌린다. 재시도도 실패하면
  독립 심사를 통과하지 못한 것으로 보고 `needs-human`으로 멈춘다.
- `REJECT` 항목이 정해진 필드를 빠뜨렸으면 형식 오류로 처리한다. 작성자가 의미를 추측해 고치지 않는다.

## 종료 조건

- 1차와 2차가 같은 판본에 차례로 `PASS`해야 최종본이다.
- 한 번이라도 수정하면 이전 `PASS`는 무효다.
- 작성자는 형식에 맞는 `REJECT` 항목을 면제할 권한이 없다. 수정할 수 없는 항목 하나만 있어도
  최종본을 내보내지 않고 `needs-human`으로 멈춘다.
- 전체 수정 주기는 최대 세 번이다. 세 번째에도 `REJECT`이면 unresolved 항목과 필요한 사람의
  결정을 적어 `needs-human`으로 멈춘다.
- 심사자가 근거와 충돌하는 수정을 요구하면 따르지 않는다. 충돌 지점과 원문 근거를 남겨
  `needs-human`으로 넘긴다.
- 최종 응답에는 사용자가 요구한 원고만 먼저 제시한다. 심사 과정과 판정표는 요청받았을 때만 붙인다.
