# Code Writing Skill (antislop-code)

`antislop-code` is a **general-purpose code skill**. It does not impose one
style or one language. It chooses names, structure and abstraction that fit
the repository at hand — the same way `antislop-design` chooses layout and
type that fit the brief rather than one house look.

## When to Use

- Writing a new module, function or feature that another person will read, run or maintain later.
- Reviewing a pull request, a contribution, or a handoff before it ships.
- Diagnosing an existing file or directory without changing it.
- Revising only what needs to change while preserving behaviour and tests.
- Converting a generated draft, a template, or a scaffold into the codebase's own conventions.

Do not apply it to a throwaway script run once and discarded, a one-off
data-cleaning pass with no second reader, or bindings generated by a tool
from a schema or an IDL — those are not read or maintained the way a library
or a contribution is. Apply it to code in any language: the catalogue below
is about shape, not syntax.

Treat "write" or "implement" as authoring, "review" or "look this over" as
diagnosis, "fix" or "clean up" as revision, and "port this" or "make this
fit our style" as conversion. Do not attach a findings table the caller did
not ask for; lead with the finished code.

## Quality Priority

Judge in the following order. Do not damage an earlier condition to gain a
later advantage.

1. **Behaviour and tests**: the code does what it must, and the tests that prove it still pass.
2. **Fit with the codebase**: the change reads as if the same person who wrote the surrounding code wrote this too — same naming, same error handling, same structure.
3. **Clarity**: a maintainer who has never seen this file can follow it without asking the author.
4. **Brevity**: nothing exists that the first three conditions do not require.

## What Code Slop Is

Code slop is a structural or naming choice that could be dropped into any
codebase, in any language, unchanged, and would still "look like good
code." It is the engineering equivalent of a sentence that fits any topic.
The test is not whether a pattern appears — an interface, a try/except, a
comment can all be correct — but whether the choice was earned by this
code's actual shape or is the generic default a model reaches for when
nobody decided otherwise.

- **A comment that restates the line.** `// increment the counter` above `counter += 1`. The comment adds nothing the code did not already say.
- **A docstring on a getter.** `"""Gets the name."""` above `def get_name(self): return self._name`. The name of the method already is the docstring.
- **A guard for an impossible state.** A null check, a type check or an `assert` on a value the caller can never actually pass, defending against a state the type system or the call graph already rules out.
- **A try/except or try/catch that swallows.** `except: pass` or `catch (e) {}` — the failure disappears instead of propagating or being handled.
- **An interface or abstract class with one implementation.** A `Repository` interface with exactly one `SqlRepository` behind it, built for a substitution that will never happen.
- **A factory for one class.** `createWidget()` that only ever returns a `Widget`, adding a layer of indirection with no second product to switch between.
- **Names like `Manager`, `Helper`, `Utils`, `Handler`, `Service` with nothing behind them.** A class named for a role instead of what it actually holds or does, often a grab-bag of unrelated methods.
- **A wrapper that only forwards.** A function whose entire body calls another function with the same arguments and returns its result, adding a name but no behaviour.
- **A constant made configurable that never varies.** A value read from an environment variable, a config file or a settings object that has exactly one value in every environment that exists.
- **Dead code kept "just in case," or commented out.** A branch nothing reaches, an unused parameter, a block of commented-out code sitting next to the code that replaced it.
- **"Robust," "enhanced," "improved," "comprehensive" in a name, a comment or a commit message.** A quality claim standing in for a specific change; the word describes nothing a reader can check.
- **A TODO or FIXME that ships.** A marker for work that was never done, left in the code that goes out anyway.
- **Logging every step.** A `print` or `log.info` call after every line, drowning the one log line that would matter in noise.
- **A generic error message.** `raise Exception("Something went wrong")` or `throw new Error("failed")` — no failing operation named, no next step suggested.
- **Type or annotation noise that repeats the obvious.** `count: int  # an integer` or a return-type annotation restating what the function's own name already says.
- **Re-exports and barrels nobody imports.** An `index.ts` or `__init__.py` re-exporting everything in a directory when nothing outside it imports through that path.
- **A test that asserts the implementation instead of behaviour.** A mock call count, a check that a private method ran, in place of a check on the return value or the observable state.
- **A commit message that praises itself.** "Successfully implemented the feature" or "now works perfectly" — a self-assessment where a commit message names what changed.

### How to see these in source

Most of these markers have a concrete textual signature: a bare
`except:`/`catch (e) {}` with an empty body, a class name ending in
`Manager`/`Helper`/`Utils`/`Handler`/`Service`, an `interface` or abstract
base class with exactly one class implementing or extending it, a `# TODO`
or `// TODO` comment, a comment line whose words are the same words as the
code line beneath it, a `raise`/`throw` with a generic string literal, a
config or environment lookup for a key whose value never changes across the
codebase's own config files, and a commit message containing "successfully"
or "robust." The full table of markers, a grep-able pattern for each, and
the fix, is in
[references/catalogue.md](references/catalogue.md).

## The Decisions a Specific Change Makes First

Before writing or changing code, settle the following. These outrank the
catalogue whenever they conflict with it.

1. **The repository's own conventions outrank the pack.** A sample of how this codebase already names things, handles errors and structures modules outranks any rule in this skill. Read two or three neighbouring files before writing one more.
2. **The smallest change that passes the check.** Do not restructure a file to fix one line; do not introduce a pattern the rest of the codebase does not use.
3. **Delete before add.** If a change can be made by removing code, remove it before reaching for a new abstraction, a new flag or a new file.
4. **A name says what, a comment says why, or nothing.** A comment that would still be true if the code beneath it changed is not doing its job; a comment that repeats the code is not doing its job either.
5. **An abstraction is earned by a second caller.** Do not generalise, interface, or configure something for a future need that has no present caller.
6. **A guard is earned by a reachable state.** Check for a condition only when something in the code's actual inputs or call sites can produce it.
7. **An error message names what failed and what to do.** "Config file not found at <path>; run `init` first" beats "Something went wrong."
8. **A test tests behaviour.** It asserts on inputs and outputs or observable state, not on how many times an internal method was called.

## The Four Tasks

### Write

1. Read two or three files near where the change lands: naming, error handling, module shape, test style.
2. Write the smallest version that satisfies the requirement and the existing conventions, real inputs and real error paths, no placeholder data.
3. Run the checklist in [Verification](#verification) before calling it done.

### Diagnose

Do not change the source. Produce a findings table and nothing else:

- What to preserve (behaviour that works, tests that pass, conventions already followed correctly).
- Findings: `file:line | marker | effect on the maintainer | one-line fix`.
- What a human must decide.
- Overall verdict.

Do not flag a marker you cannot pin to a location and a maintenance effect;
do not flag a single weak marker alone (see [Strength Tiers](#strength-tiers)).

### Revise

Hold a preservation contract. Do not add, remove or alter the following
while fixing what was flagged:

- **Behaviour**: what the code does for every input it already handles.
- **Public API and signatures**: function names, parameters, return shapes and exported symbols that other code calls.
- **Tests**: an existing passing test keeps passing; do not weaken an assertion to make a change fit.
- **Error messages**: a message another system or a log parser depends on, unless the brief asks for a specific message change.
- **Performance characteristics**: an complexity or resource bound the code was written to hold.
- **Anything the brief marks as kept.**

Be able to state the problem each change solves. Do not swap one name or one
structure for another only to look different. Stop at `needs-human` when the
brief or the codebase's own convention is too unclear to safely settle a
change.

### Convert

Take a generated draft, a scaffold, or a template and rebuild its names,
structure and error handling around the target codebase's own conventions,
keeping the behaviour and the public surface the draft already has. This is
not a rewrite for style alone: only change what would mark the file as
having come from somewhere else.

## Strength Tiers

- **Strong markers act alone.** One instance is enough to flag: a swallowing catch, an interface or abstract class with exactly one implementation, dead or commented-out code, a shipped TODO, invented "robust"/"enhanced" naming.
- **Weak markers act only when two or more overlap in the same function or file.** A short comment alone is not slop; a single defensive check alone is not slop; one `Helper`-named class alone is not slop. Two or three of these together, doing no other work, are.

Do not run the catalogue as a checklist of banned constructs. A try/except,
an interface and a comment are ordinary tools; the question is always
whether this use, in this code, was decided or defaulted to.

## Five Questions Before a Cut

Before removing anything flagged, check all five:

1. Does behaviour change if this is removed?
2. Is it the author's deliberate choice, or something a template or a generator left behind?
3. Does it explain something the code does not already say, or does it restate the code?
4. Does it guard a state the code's actual inputs or callers can reach?
5. Would the maintainer trust this file more with it gone?

## Verification

- Do the existing tests still pass, and does a new test cover the behaviour that changed?
- Does the change read as if it were written by whoever wrote the surrounding file?
- Would a maintainer who has never seen this file understand it without asking the author?
- Is every abstraction, interface and factory backed by a second real caller?
- Is every guard defending a state the code can actually reach?
- Does every error message name what failed and what to do next?
- Is anything present that behaviour, fit or clarity did not require?
- Are any strong markers present — a swallowing catch, a one-implementation interface, dead code, a shipped TODO, invented "robust" naming? One is enough to flag.
- Do two or more weak markers overlap in the same function or file — a short comment, a single guard, one generically named class, together?
- For a revision: does the preservation contract hold — same behaviour, same public API, same passing tests, same error messages, same performance characteristics?

## Editorial Review

Do not close out a change meant for another maintainer — a library release,
a contribution, a handoff — on the writer's own judgment alone. Bind a
`review` check to the change in a scenario:

```yaml
- id: roster-review
  then: the roster module passes the reviewer and the maintainer
  check: { type: review, pack: code, path: src/roster.py, contract: docs/roster-brief.md }
```

- `path` is the file or directory under review; `contract` is the brief describing what the change is for, who maintains it, and any stated conventions.
- The harness runs `reviewers/code/1-reviewer.md` first, and only on a pass runs `reviewers/code/2-maintainer.md`. A stage passes only when the entire response is exactly one line, `PASS`.
- The scope skill proposes this check only when the code will be read or maintained by someone else — a library, a contribution, a handoff. For code nobody else reads or runs again, `vibe size` is the code gate instead.
- If the same failure repeats twice, stop at `needs-human` rather than guessing at a fix the reviewer did not ask for.

This mirrors the two-stage independent review in `antislop-design`'s
[Editorial Review](../antislop-design/SKILL.md#editorial-review) — a
different reader judges, the writer does not self-certify, and a reviewer
returns only `PASS` or a `REJECT` list, never a rewrite.

## Pitfalls

- Do not strip the repository's own conventions to match this pack. When the two disagree, the sample outranks the rules.
- Do not remove a comment that explains why a choice was made, even a short one; only remove a comment that restates what the code already says.
- Do not delete a guard whose state is actually reachable, even if it looks defensive; check the call sites before cutting.
- Do not rewrite a test to make it pass instead of fixing the code, and do not weaken an assertion to quiet a failure.
