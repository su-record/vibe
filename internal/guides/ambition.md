# Take on the larger problem

Use when a request is visibly one slice of a larger problem the user keeps returning to, when the user asks what more this could do for them, or when an outcome will take several sessions. The effect of this work grows with the size, difficulty and horizon of the problem; a question with a paragraph answer barely uses it. A request that stands alone is done as asked: do not turn every task into a programme.

Name the larger problem once. Finish the requested work first. Then, only on observed evidence (the same kind of request recurring, a saved note, the user's own description of the aim), say in two or three sentences what the larger outcome is, what you saw that points to it and what taking it on would involve. Offer it; do not start it. If the user declines, record that and do not raise it again until new evidence appears. Never invent a problem to look ambitious.

Keep the user's problems in one living note, `problems.md`, in existing knowledge; the brief reads it with the other priority notes. For each problem record: the problem in the user's words, why it matters to them, the evidence with its date and source, how often or how long it costs them when known, what a machine could check about a solution, and its state (noticed, offered, declined, taken, done). Mark a hypothesis as a hypothesis. Personal knowledge holds problems that cross projects; project knowledge holds the project's own. Update entries; do not append a new note per session.

Make the work checkable before making it large. Capability is uneven: it is strongest where the result is digital and a machine can decide right from wrong, and weaker elsewhere. So for each part of a larger problem ask two questions before promising anything. Is the input and output digital and reachable from here? Can a machine decide whether the result is correct? Where both hold, write the check first; long unattended work is safe only behind it. Where the result cannot be judged mechanically, first try to build a judge (a known-good sample to compare against, a schema, a rendered output, a reproducing input). If none is possible, say at the start that this part needs the user's eyes, expect weaker results there and keep it small. A physical or offline step belongs to the person.

Run a long outcome as milestones. Each milestone ends in something the user can use and a check that decides it. Keep one tracked intent and the existing check engine; use the system guide when the outcome is several connected workflows. Between milestones continue within the authority already given without asking again; stop for a missing decision, new authority or an external action. On resumption start from recorded evidence and the note, not from memory of having finished.

Say when access limits the result. If the current model, reasoning setting, context size or available tools visibly constrain a problem you have taken on, tell the user once what the constraint is and what a stronger setting would change. Report only what you can observe in this host; do not guess at other tiers. Continue with what is available and never switch models, buy access or raise a spending setting on your own.

Explain the proposal in the user's language: what the larger problem is, what would be built first, what it costs to run and maintain, which parts a machine will check and which they must read. Do not claim an effect without a comparable baseline.
