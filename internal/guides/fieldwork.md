# Learn from the user's actual work

Use when understanding a recurring workflow, resolving a mismatch between tests and actual use, applying a user correction, or deciding whether a repeated fix should become a reusable capability. Ordinary isolated edits need no extra discovery stage.

Start with the conversation and relevant existing knowledge. Observe accessible samples, actual outputs and how the user currently completes the task. Identify only the concepts and actions needed for this outcome: what the user means by a record/document/customer, what changes its state, who decides, and what happens on an exception. Record local meanings rather than imposing textbook definitions. A schema describes stored fields; it may not explain what those fields mean. Distinguish observed facts, user-confirmed decisions and hypotheses with their source, date and applicable environment. Ask about a consequential gap only after checking available evidence; never infer private workplace behavior from a generic interview template.

Preserve the ability the current workflow gives the user. Before replacing a format or tool, check how they inspect, edit, approve or recover its output. An inefficient-looking manual step may be their only quality check. Use representative real input within existing authority. A production write is not justified merely to gain realism.

Treat corrections as changes to future behavior. Apply the correction to the current work first, then update the relevant existing note with what was wrong, the corrected understanding, scope/source and the next action that should differ. A one-task exception is not a permanent personal preference. Replace the superseded claim or mark it explicitly as superseded; do not leave two competing current rules. Current user instructions and project rules take precedence over saved defaults. Never store credentials or treat a note as new permission.

Verify at the point of use when accessible: target OS/app/version, real input, the action the user needs, observable output and important failure/recovery behavior. Keep local tests, target-environment execution and user acceptance separate. If the target is unavailable, record the exact remaining observation in the existing task context and report the implementation's verified scope. Continue other authorized work; do not invent acceptance or require a new model review. On resumption, revisit that observation only when relevant access, input or evidence has changed.

When work reveals a repeated workaround, identify its shared cause and consider the existing extensions guide before adding code. Keep one-off fixes local. Promote a solution into a reusable tool/skill only when observed recurrence or a concrete next use justifies maintenance and the user has authorized that implementation scope. Keep project-specific vocabulary/configuration outside general logic. A temporary workaround needs a removal/replacement condition; a reusable capability needs a maintained source and representative checks. Do not rewrite the platform after every task or turn repeated mistakes into a growing blanket prohibition list.

Retain only durable, useful findings in the existing knowledge directory. Update an existing relevant file first. When a stable note is needed, `work-context.md` can hold the workflow and open observations, `corrections.md` the currently applicable corrections, and `reuse.md` useful repeated solutions and temporary-workaround exit conditions. These optional filenames are prioritized by the existing brief in project and personal knowledge; they are not three required reports. Existing `knowledge add` with titles `work-context`, `corrections` or `reuse` writes these files, replacing their contents, so read and preserve still-valid content before updating. Personal notes contain confirmed cross-project preferences; project notes contain project-specific operating facts. Do not copy customer material into personal knowledge indiscriminately.

Close the learning loop with observable consequences: what became usable, which assumption was corrected, and what the next relevant task can reuse. Report measured improvement only when there is a comparable baseline; otherwise keep it qualitative. Note existence, a passing test and a confident explanation do not establish better agent judgment or business value.

When a confirmed failure recurs, prefer a small reproducing check connected to the existing verification path over another blanket warning. Verify that the check fails for the old behavior and passes for the correction; preserve legitimate cases. Keep semantic or user-specific judgments as scoped guidance when they cannot be mechanically checked. Once a maintained check covers a rule, remove redundant prose only after checking its callers and preserving the reason and any uncovered boundary. Do not create a recurring audit, new model review or extra public skill for this learning loop.
