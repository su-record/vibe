# Find work AI can take over

Use this procedure only for a request to find automation opportunities in the customer's work. The output is an agreed working pilot, with an evidence-backed selection. It is not a promise of hours saved or an instruction to install an arbitrary tool.

1. Establish the observation window and accessible sources: work logs, exported mail, documents, tables, meeting notes. Reuse available readers and connectors. Name inaccessible sources; never assume access to the customer's whole week. If there is no useful sample, request a small export or prospective time log and explain what remains unknown.
2. Group distinct work events with stable IDs and source references. Deduplicate repeated exports and the same event appearing in mail, notes, and a table. Record observed counts, active minutes, and how many events have measured duration. A meeting's full length is not preparation time; a forwarded productivity claim is not this customer's evidence.
3. Keep one compact opportunity register. Each grounded candidate names the customer problem, counting rule and source references, observed frequency/duration coverage, input/output, existing capability or required tool/connection, setup, failure cases, permissions/external effects, human review point, rollback, and an executable feasibility/acceptance check. Label missing quantities and unverified access as unknown; unknown is not zero.
4. Separate measured current effort, a hypothesis about automatable steps, and the pilot's observed results. Human time saved needs a comparable manual baseline and measured setup, correction, and review effort. Report machine runtime separately. Without the necessary usage, labor-value, implementation, and maintenance data, savings, monetary ROI, and payback remain unknown. Do not invent failure probabilities or implementation hours.
5. Rank only eligible candidates: feasibility/permission first, then the customer's objective, then evidenced recurring burden and implementation needs. Ask for a priority if it changes the choice. Explain uncertainty and show up to three supported candidates; fewer is fine. Do not fabricate a third item or force a numerical ROI ranking. A blocked connection is a prerequisite to resolve, not an installed tool.
6. Give each grounded candidate an observational check or a clearly named prerequisite. Agree on one pilot and activate only its build scenarios. If none is feasible, record the limiting evidence/access and the smallest next step; do not claim installation. Keep other candidates as future choices, not additional implementation obligations.
7. For the selected pilot, reuse installed tools and give exact local setup and rerun commands. Prefer a reversible local installation with a manifest of created files. Verify original input, changed input, missing/invalid input, repeat execution, source preservation, and rollback. Each scenario must bind to a check that the agent can execute without a judge key. File existence alone does not prove that an automation works.
8. Mark sends, payment, deletion, permission changes, and production updates explicitly. Preserve the user's existing authorization within its scope; get a concrete action approved if it is not covered. Keep human review before any external effect that requires it. A local draft or simulated connector proves its local behavior only.
9. Hand over the chosen pilot's command, checks and evidence, source/permission limits, and rollback. Report observed behavior and measured quantities separately from hypotheses. Completion is the selected checks' verdict; customer ROI remains unverified until it is measured.
