# 이해할 수 있는 자세한 설명: 비교 예시와 평가 기준

아래 답변은 주어진 사실에 맞춰 작성한 참고 예시다. 실제 모델 평가나 사용자 이해도 테스트를 통과한 기록이 아니다. 배포 후 실제 대화를 평가할 때 사용하며, 매 작업마다 읽거나 별도 모델 평가를 실행하지 않는다.

| 상황과 주어진 사실 | 개선 전 표현 예시 | 기대하는 설명 예시 |
|---|---|---|
| 일반 수정: 중복 주문 방지 코드와 재실행 검사 통과. 운영 확인 없음 | 멱등성 보장 및 테스트 그린 | 다시 실행해도 같은 주문이 두 번 만들어지지 않게 수정했고, 자동 검사로 확인했습니다. 운영 환경에서는 아직 확인하지 못했습니다. |
| “에이전트의 판단?”: 경로·명령 기반 위험 감지와 필수 검사 존재. 모든 업무 위험 탐지 불가 | 에이전트 판단을 게이트로 보완합니다 | AI가 필요한 검사를 고르되, 접근 권한처럼 민감한 변경은 정해진 검사가 빠지면 완료로 처리하지 않습니다. 다만 파일 이름과 실행 명령만으로 모든 위험을 찾을 수는 없습니다. |
| 검사 실패: 수정됨, 로그인 검사 실패, 후속 검사는 선행 실패로 미실행. 수정 권한 있음 | 구현 완료, 일부 검증 이슈. 로그를 확인하세요 | 수정은 했지만 로그인 검사가 실패했습니다. 그다음 검사도 아직 실행되지 않아 완료 상태는 아닙니다. 실패 원인을 확인하고 고치겠습니다. |
| “배포만 남은건가?”: 자동 검사 통과, 실제 앱 실행 확인 없음, 배포 안 함 | CI 그린이므로 릴리스 가능 | 자동 검사는 통과했지만 실제 앱에서의 작동 확인이 남았습니다. 아직 배포하지 않았습니다. |
| 배포: 패키지 게시·다운로드 확인, 기존 앱 업데이트 여부 모름 | npm publish 성공 | 새 버전을 배포했고 다운로드되는 것까지 확인했습니다. 지금 사용 중인 앱에 새 버전이 적용됐는지는 아직 확인하지 못했습니다. |
| 선택 필요: 실패 시 재시도하면 중복 결제 가능, 자동 취소 수단 없음 | Retry policy를 선택해주세요 | 결제 실패를 표시하고 멈추는 방식을 추천합니다. 자동으로 다시 시도하면 같은 금액이 두 번 결제될 수 있고 자동 취소도 안 됩니다. 대신 일부 주문은 직접 확인해야 합니다. |
| 기술 상세 요청: 실패한 검사 ID가 payment-retry, 예상 주문 1개·실제 2개 | 초보자용 비유를 반복 | `payment-retry`는 결제를 다시 시도해도 주문이 하나만 생기는지 확인하는 검사입니다. 예상은 1개였지만 실제로는 2개가 만들어졌습니다. |

평가할 때는 먼저 답변을 사실과 대조한다. 실패·미실행·미확인을 성공으로 바꾸거나, 현재 변경에 오래된 성공 기록을 붙이거나, 중요한 위험·조건을 빼거나, 승인된 수정을 사용자에게 떠넘기면 실패다. 쉬운 문장이라도 이 기준을 만족하지 않으면 안 된다.

이후 사용자가 무엇이 달라졌는지, 왜 그 방식을 택했는지, 어떻게 작동하는지, 어디까지 확인됐는지, 자신의 결정이 필요한지 파악할 수 있는지 살핀다. 필요한 이유나 작동 원리를 생략한 짧은 답변은 충분한 설명으로 보지 않는다. 단어 수나 전문 용어 개수만으로 합격 처리하지 않는다. 실제 이해도는 사용자 피드백으로 확인한다.
