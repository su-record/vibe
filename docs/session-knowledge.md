# Session knowledge

## Why

A person who wants a knowledge hub should not have to say "save this". vibe already asked the model to retain useful context, but whether it did was left to the model, and nothing turned repeated work into better methods or skills. Session knowledge makes the keeping regular, for the people who choose it, in both Claude Code and Codex.

The wiki is the knowledge base of the person's FDE, and its reader is the model: it is there so the model chooses better, fills in what the person and capable models leave unsaid, and proposes improvements fitted to how the person works. Nobody is expected to browse it.

## What it does

- `vibe knowledge auto on` turns it on for this computer; it is off by default. The settings live in `~/.config/vibe/knowledge.json`, outside every project.
- The personal Stop hook gives the working model one knowledge turn after a turn that changed project files, and after every `--turns` conversation turns (default 5; 0 keeps only the file trigger). It appends one fact line to `log.md` (time, `[[projects/<name>]]`, client, revision, what triggered it).
- The model, which already holds the conversation, keeps what is durable in the wiki, records better methods, and for a repeated procedure drafts a skill and offers it (`--skills propose`, the default) or installs and reports it (`--skills create`). It tells the user in one line, or says nothing when nothing qualifies. The `wiki` guide holds the rules.
- `--dir <folder>` moves the wiki; pages are plain Markdown with `[[links]]`. The brief reads `index.md` with the other priority notes. A folder is stored by its real path, so a linked vault stays readable.
- Obsidian (4.2.15): turning on without `--dir` uses a `vibe` folder inside the vault Obsidian has open, or most recently used, and copies an earlier wiki into it when the new place is empty (nothing is overwritten or deleted). Without Obsidian the wiki stays at the default folder, made ready as a vault (`.obsidian/`); every session start checks Obsidian's own vault list (`obsidian.json`), and the first one after Obsidian has run adds the wiki to that list, keeping everything else in the file. The output warns when the folder is synced off the computer (iCloud, Dropbox, OneDrive, Google Drive, Obsidian Sync).
- Projects (4.2.16): each project folder gets one page name, its folder name or, when another folder already holds that name, the name with a short mark; the names live in `~/.config/vibe/knowledge-projects.json`. In a vibe project, every session start links the project's shared knowledge (`.vibe/knowledge/`) into the wiki as `projects/<name>/` (a junction on Windows), so Obsidian shows and edits it in the same vault. No link goes into a synced wiki or a wiki inside the project. On a knowledge turn the model puts what the project's team needs into `.vibe/knowledge/`, which shows in git for the user to commit, and keeps the rest personal. The brief and `vibe context` read the project's own page whatever the task's words.
- Index (4.2.17): every session start that links a project rewrites a marked block in `projects/<name>.md` (`<!-- vibe:shared-knowledge -->`) with one line per shared subfolder linking each page (at most 200), and adds the page's line to `index.md` when the index has none. Everything outside the block and every other index line is left alone, and a file is written only when its text changes. So every shared page is reachable from the index; `vibe knowledge lint` reports a shared page added since then as unlinked.
- Finding (4.2.18): `vibe knowledge find <words…>` ranks the wiki's pages, the project folders it shows and the current project's `.vibe/knowledge/` by the words: a word in a page's title or file name or `aliases` counts most, then `tags`, `summary`, headings and up to three mentions in the text, and pages matching more of the words rank first. It reads every page each time (no model, no index file) and prints each page's link, title, summary and tags. The `wiki` guide asks the model to run it before saving, update the page that holds the subject instead of adding a near-duplicate, link one to three related pages with the reason, and start pages with Obsidian properties (`summary`, `tags`, `aliases`, `updated`) and a title that names the subject. `aliases` may hold the user's own words in their language, the one exception to English records, so a search in that language finds the page.
- Journal (4.2.18): while session knowledge is on, a UserPromptSubmit hook and a PostToolUse hook on shell calls append one line each to a private journal per project folder (`~/.vibe-runtime/journal-<hash>.jsonl`, owner-only, outside every project and the wiki): the prompt's first 600 characters with keys, tokens, `password=` values, long opaque strings and e-mail addresses masked, and whether it pushed back on the last answer; for a shell call only the command words (`git push`, `npm run`) and whether it worked. Lines older than 30 days, and the oldest past 2000 lines or 1 MB, are dropped. `--journal off` stops it. The hooks run `hooks/journal.cjs`, which reads the settings before loading anything else (about 27 ms per call while off, 46 ms while on, measured on the development machine).
- On a knowledge turn the reason says what the journal holds since the last one, the journal gets a mark, and `vibe knowledge journal` prints the recent prompts, corrections and failed commands, and the repeats of 30 days found by code: an instruction given at least three times in two sessions (by word overlap), three commands run in the same order three times in two sessions, a command failing twice. The model works from that instead of its memory, records the defaults and expectations the person leaves unsaid, and proposes at most one improvement, the lightest that removes a repeat (a default, a rule, a prompt, a script or tool, a check or hook, a skill), tracked in the wiki's `proposals.md` with its evidence and outcome; a declined one is not offered again without new evidence.
- Before choosing: the session start tells the model, while session knowledge is on, to run `vibe knowledge find <subject>` before choosing an approach, a tool or a design, and to follow current decisions, reuse methods and avoid recorded problems.
- Page types: a page's `type` (`decision`, `method`, `problem`, `fact`, `project`, `research`, `skill`, `proposal`) tells the model whether to follow, reuse, avoid or just know it; `find --type` narrows to one and the lint reports other values. A page naming another in `supersedes: "[[old]]"`, and a page with `status: archived`, keep a third of their score and are marked, so current knowledge comes first and old reasons stay readable.
- `--exclude <folder>` keeps work there out of the wiki: no fingerprint, no log line, no journal line, no knowledge turn. `--include` removes the exclusion.
- `vibe knowledge lint` reports broken links, orphan pages and pages over 200 lines. It follows each linked project folder once; those pages are checked but never called orphans.

The hooks read no transcript, start no model and resolve no PATH command. It skips the home folder and stays quiet when the session or folder cannot be identified.

## Cost

Each knowledge turn is one more model response. The file trigger runs at most once per changed turn; the conversation trigger once per `--turns` turns. On a large project the fingerprint adds up to about 1.5 seconds per Stop. Every prompt and shell call starts node once for the journal hook, whether or not session knowledge is on (about 27 ms while off).

## Verified

Hook behaviour (off by default, both triggers, the continuation guard, exclusion and inclusion, a wiki inside the project, the home folder), settings validation and the wiki lint run in `src/core/knowledge-auto.test.ts`, `src/core/knowledge.test.ts` and `src/core/knowledge-lint.test.ts`; project names, links and the index block in `src/core/knowledge-projects.test.ts`; properties, query words, ranking, types, `supersedes`, `status` and the `find` command in `src/core/knowledge-find.test.ts`; masking, command words, outcomes, retention, repeats, the journal hooks, exclusion, `--journal off`, the knowledge turn's journal clause and mark, the session start's recall line and `vibe knowledge journal` in `src/core/knowledge-journal.test.ts`; the project page in the brief and context in `src/cli/internal.test.ts` and `src/core/context.test.ts`.

## Not verified

- Whether models keep useful pages and stay silent when nothing qualifies, and whether later sessions save more tokens than the knowledge turns cost. This needs a bench.
- Codex continuing a turn on a Stop `block` was not run against a live Codex; vibe's existing Stop hook relies on the same behaviour.
- Whether models run `find` before saving and write useful summaries, tags and aliases; ranking is by words, so a page that uses other words for the subject is found only through its aliases.
- The journal hooks against live clients: Codex 0.163's binary names UserPromptSubmit, PostToolUse and the `prompt`, `tool_input` and `tool_response` fields, but no live Codex or Claude Code session was journaled. Whether a shell call worked is read from `exit_code`, `exitCode`, `returnCode`, `status`, `interrupted` or `is_error`; when a client reports none of them the line says unknown, and failures are then not counted.
- Masking is by pattern: a secret in an unusual shape can reach the journal, which stays owner-only on this computer.
- Whether the found repeats lead to proposals the person accepts, and whether accepted ones stop the repeat. This needs use over weeks.
- Whether models split shared and personal knowledge as the guide asks.
- How a sync service treats a folder link was not checked; that is why a synced wiki gets no link.
- The Obsidian connection is tested against the registry format, not a running Obsidian. An Obsidian window open while the list is written may keep its own copy until it restarts; the next session start adds the entry again if it was lost.
